# Repository merge and convergence rules

## Owner directive: additive best-of-best history-verified merges (2026-11-18)

Inspect complete available Git ancestry to its roots, historical branches, tags, deleted/renamed paths, and paginated open, rejected, closed and merged pull requests (including PR head/merge refs) before any code replacement. Compare actual delivered pre/post source and API/behavior inventories; merge ancestry alone does not prove capabilities survived. Record bad commits and lost code and restore previously proven improvements via canonical Synexia Maven/OpenRewrite recipes without rebasing useful history.

Treat original upstream and earlier accepted extensions as protected backward-compatible subsets. Select the strongest verified correct atoms and combine compatible capabilities into additive superset APIs without breaking existing types, ABI, behavior, serialization, reflection, exception/null/ordering semantics or memory/runtime guarantees. Require API, compiler, unit and runtime regression evidence; never replace a working feature merely because a candidate is newer.

Prefer Apache-2.0 for new eligible original code; honor existing project/per-file upstream licenses, attributions, NOTICE, exceptions, and dependencies, including Apache variants, LLVM exception, EPL and GPL where relevant. Abstract algorithms may be independently implemented from legitimate specifications, but LLM rewrites do not automatically cure copyright/license issues; avoid copying protected expression, and assess applicable patent rights.

Record last-checked date and exact commit SHA, root/ref/PR pagination coverage, source-loss findings and tests in the canonical private `hsoliwal/com.synexia/docs/M3-SCALE/invariants/SYNEXIA-HISTORY-REVIEW-LAST-CHECKED.tsv` ledger. PARTIAL remains PARTIAL until full history, actual delivered code and regression tests have been examined. Keep recipes and convergence evidence in the Synexia owner; receiving projects retain only compatible deliverables and tests.
